No systemd, no GRUB, no PAM at login: three deliberate omissions in DimOS

Most Linux distributions inherit the same three defaults: systemd as init, GRUB as bootloader and PAM for authentication. They are good defaults for general-purpose systems. DimOS, the hardened Linux distribution I'm building from scratch, ships none of them in its core path.

This post explains why, and what each decision costs. The rule behind DimOS is simple: every component gets in by a conscious decision, not because another distro had it. Each of these three replacements is smaller and easier to audit. None of them is free.

1. No systemd: s6 as init

DimOS uses s6 from skarnet.org as PID 1. The whole s6 family, including its supervisor, logger and scripting language, weighs about 1.5 MB of binaries.

Size isn't the main reason, though. The difference is where decisions happen:

  • With systemd, PID 1 decides what to do when a service dies: whether to restart it, how many times, with what backoff.
  • With s6, every service gets its own tiny supervisor, s6-supervise. When the service dies, its supervisor restarts it. PID 1 (s6-svscan) only watches the supervisors, so a service stuck in a crash loop never touches PID 1, and never affects the other services.

A service is a directory, not a unit file: a type file (longrun for daemons, oneshot for tasks that run once) and a run script, usually in execline, a tiny scripting language with no subshells or surprises. Logs work the same way: each service can have its own s6-log, writing plain rotated text files. grep, tail and less are the whole log tooling.

What it costs: there's no systemctl, no automatic socket activation, and no ecosystem of ready-made unit files. Every service in DimOS is written by hand. That's work, but it also means I know exactly what each one does.

2. No GRUB: limine as bootloader

GRUB 2 can do almost anything: chainload other operating systems, script, read dozens of filesystems. For DimOS that's the problem. It needs separate builds for BIOS and UEFI, its configuration is generated by scripts, and all that code has a security history: BootHole (CVE-2020-10713) let an attacker run code during boot through the GRUB config parser.

I also ruled out the alternatives:

  • systemd-boot is small and simple, but UEFI-only, and adopting it opens the door to the systemd ecosystem DimOS deliberately avoids.
  • U-Boot makes sense on embedded boards, but on a machine whose firmware already speaks UEFI it's an extra layer with nothing to add.

DimOS uses limine: a single binary that boots BIOS, UEFI and CD from the same release, around 300 KB per architecture, with a flat KEY=VALUE config. The same limine.conf works on x86_64 and arm64; only the console device changes. It does exactly what DimOS needs, which is to load a kernel, an initramfs and a command line, and not much more.

It also fits the reproducibility goal. limine is pinned to a specific commit hash, so the same source always produces the same bootloader, and the Linux CLI is compiled locally from a single C file with no dependencies beyond libc.

What it costs: a smaller community and fewer answers online when something exotic breaks. Some things took work: DimOS gained A/B kernel updates on UEFI in version 0.10 and optional Secure Boot with each node's own key in 0.11, both built around limine.

3. No PAM at login

PAM is flexible: it lets any program delegate authentication to a stack of loadable modules, from passwords to hardware tokens to LDAP. That flexibility is also attack surface. Every module is shared code loaded into processes that handle credentials, and every stack is a configuration that can be wrong.

In DimOS, the login path doesn't use it:

  • login, su and passwd come from shadow-utils built with --without-libpam.
  • OpenSSH is built with --without-pam.
  • doas, the sudo replacement, uses --with-shadow.

All of them check the password directly against /etc/shadow with musl's crypt(). That removes a whole class of problems from the most sensitive path in the system: module loading, injected shared libraries and misconfigured stacks.

PAM isn't gone entirely, and I want to be precise about that. The desktop profile ships Linux-PAM for one program: the screen locker, swaylock, which DimOS builds against PAM. Its stack uses pam_unix, and a default-deny pam.d/other catches anything without its own configuration. Servers built with the base or server profile don't install it at all.

What it costs: shadow-utils refuses to make passwd setuid without PAM, so today only root can change passwords. That's fine for a single-admin system, but multi-user support will mean either enabling PAM or setting the setuid bit deliberately. Hardware tokens and directory services like SSSD would need PAM too. If DimOS ever needs them, I'll revisit this decision with eyes open.

When this makes sense, and when it doesn't

None of this means systemd, GRUB or PAM are bad. They're the right defaults for distributions that have to run on every kind of hardware and support every kind of user. Their flexibility is the point.

DimOS has a narrower goal: a small, auditable system for servers and cluster nodes that I can understand end to end. For that goal, each replacement trades flexibility for fewer moving parts:

DefaultDimOS usesWhat you gainWhat you pay
systemds6A supervisor per service, PID 1 isolated from crash loops, plain-text logsNo systemctl, no socket activation, every service written by hand
GRUB 2limineOne ~300 KB binary for BIOS and UEFI, flat config, pinned by commit hashSmaller community; A/B updates and Secure Boot had to be built
PAM at loginDirect /etc/shadow with crypt()No module loading in the login pathOnly root can change passwords; no tokens or SSSD without revisiting

If you run a fleet of standard servers, stick with the defaults. If you're building something small where every line matters, it's worth asking which defaults you actually need.
